# Persistence Audit — Problems Found

Audited live on **2026-08-11 (Asia/Calcutta)**. This is intentionally a problems-only report.

## Live verification baseline

- I started the application locally and issued GET requests to all 28 catch-all read paths and all 27 Supply Planning GET actions. Every request returned HTTP 200.
- I queried the configured MongoDB directly. All 19 seeded Supply Planning collections are populated and match their `output/*.json` counterparts exactly after excluding Mongo `_id`. The additional `orders` collection has one document; `test` is empty.
- The server emitted no Mongo failure/fallback warning during the endpoint run. Therefore **the JSON fallback is not currently active for any populated Supply Planning collection**.
- `data_source_logs` is absent from Mongo and has no `output/data_source_logs.json`; its service path falls through to an empty result and then invents healthy/default values.
- No page component under `app/` imports `lib/dummyData.js`, imports JSON, or reads a local file client-side. All page data access goes through `fetch`. The bypass problems below are therefore in the API/service implementation or directly hardcoded React display data, not a browser-side file read.

## Remediation status — 2026-08-11

All findings below have been remediated. The table is retained as the pre-fix audit record and is no longer a description of current runtime behavior.

- The S&OP facts, demand-planning masters/workflows, review cycle, inventory policies, order rules/suggestions, dispatches, chat sessions/configuration, financial/factor configuration, imports, supplier history, PO adherence, production consensus, warnings, RCA and recommendations now have Mongo collections plus matching `output/*.json` safety-net files.
- The catch-all API hydrates its existing synchronous calculation layer from Mongo on every request. Mongo failure or an empty collection falls back to JSON and then the original deterministic/hardcoded fallback.
- The exact wrong-domain order `ORD-7F578BB4` was removed and replaced with persisted boAt order/dispatch records. No broad collection reset was performed.
- Hardcoded page summaries and chart shapes identified below now use API/DB values. Scenario outcomes without persisted calculations display “Not calculated” rather than invented numbers.
- Supply calculations now use persisted forecast, inventory, capacity, PO dates, handover dates, supplier classifications/history and constraint values. The five synthetic warning/RCA records and three synthetic executive recommendations were replaced by one set derived from the one active persisted constraint.
- Live verification after migration returned `meta.source = mongodb`, a 2026-W08–W33 S&OP horizon, reconciled lifecycle stages, `dispatch_records` provenance, DB-configured order rules, 52 DB-derived capacity rows, Mongo-only data-source lineage, and no Mongo/JSON fallback warning.

## Historical bottom line

Mongo itself is reachable and the seeded Supply Planning JSON fallback is **not** firing. The active integrity problem is the amount of hardcoded/process-memory data layered around those populated collections. The main S&OP application is almost entirely generator-backed, while several Supply Planning screens combine genuine Mongo rows with fabricated KPIs, dates, histories, curves and recommendations—often labeling the composite as live or healthy.
